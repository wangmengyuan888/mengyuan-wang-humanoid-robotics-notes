具身智能是一种**基于物理身体**进行感知和行动的**智能系统**，通过智能体**与环境交互获取信息**、**理解问题**、**基于环境做出决策并采取行动**以**实现某些目标**。

### 什么是 ROS

机器人操作系统（Robot Operating System，ROS）是一套开源软件库与工具集，用于协助开发者构建机器人应用程序。

目前，ROS 主要分为：

- ROS 1（经典版本，已广泛应用）
- ROS 2（支持分布式计算、实时性）

ROS 的每个版本都以独特的乌龟作为吉祥物，形成了一条充满创意的乌龟家族演化线。

### ROS 1 的局限与 ROS 2 的发展背景

**实时性问题**

受限于基于 TCP/IP 的通信机制，ROS1 无法提供工业场景所需的毫秒级实时响应能力，故难以满足工业自动化及自动驾驶等高实时领域的要求。

**分布式系统瓶颈**

ROS1 的集中式架构存在扩展性瓶颈（如节点变更需重配系统），难以支撑多机器人协作和大规模工业自动化等分布式场景。

**复杂场景的挑战**

ROS1 因实时性、可靠性与安全性不足，难以满足工业4.0、自动驾驶及智能物流等复杂场景的高要求。

要在资源有限的嵌入式系统中运行；

要在有干扰的地方保证通信的可靠性；

要做成产品走向市场，甚至用在自动驾驶汽车和航天机器人上。

类似的问题不断涌现，致使更加适合各种机器人应用的新一代 ROS 诞生了，也就是 ROS2。

### ROS 1 与 ROS 2 的比较

**通信机制对比**

| 特性 | ROS1 | ROS2 |
| --- | --- | --- |
| 通信方式 | TCP/IP 通信协议 | Data Distribution Service（DDS）通信协议 |
| 数据传输 | 采用自定义消息传输系统通过话题（Topic）和服务（Service）进行数据交换 | DDS 提供多种通信模式支持发布/订阅、请求/响应，可靠/不可靠传输 |
| 优缺点 | 网络不稳定时易出现延迟/丢包，缺乏实时性和 QoS 支持，难以满足高实时性/大规模系统需求 | 通过 QoS 机制实现细粒度控制，支持数据传输延迟、可靠性、带宽等配置，满足复杂网络环境的高效可靠通信 |

**ROS2 与 ROS1 系统架构的差异**

ROS1 依赖中心化 Master 和自定义协议（TCPROS/UDPROS），仅兼容 Linux；ROS2 通过去中心化架构、工业级 DDS 标准（含抽象层）及 Intra-process API 重构中间件，支持 QoS 实时通信，并扩展至 Linux/Windows/Mac/RTOS 多平台。

**ROS2 的特点和优势：ROS2 使用 DDS 数据分发服务通信协议**

在 DDS（Data Distribution Service，数据分发服务）中，QoS（Quality of Service，服务质量）是一组可配置的参数，用于精确控制 DDS 系统的行为。DDS 是一种面向实时分布式系统的发布-订阅（Publish-Subscribe）中间件国际标准（由 OMG 制定），而 QoS 机制是其最核心、最强大的特性之一。它允许开发者在不修改业务代码的情况下，通过配置来满足不同应用场景对数据可用性、传递可靠性、实时性和资源消耗的非功能性需求。

### DDS 与 QoS

ROS2 采用 DDS（Data Distribution Service）作为底层中间件，实现完全去中心化的节点自发现（Discovery 机制），节点间直接通信，无单点故障风险。

DDS 支持多种服务质量（QoS）策略，可根据不同应用需求灵活配置，确保数据传输的可靠性和实时性。

QoS 策略能实现对通信行为进行精细化调控。

| 策略名称 | 作用描述 | 典型应用场景 | 性能影响 |
| --- | --- | --- | --- |
| Deadline（期限策略） | 设置消息传输的最大允许延迟时间，超时则触发错误处理。 | 机械臂关节指令（要求 ≤10ms 送达） | 超时会导致数据丢失或报错 |
| Reliability（可靠性策略） | 选择消息传输可靠性：RELIABLE：必达；BEST_EFFORT：可丢包 | 控制指令（必达）；摄像头画面（可丢包） | RELIABLE 增加 10~30% 延迟 |
| History（历史队列策略） | 设置消息队列深度：KEEP_LAST：保留最新 N 条；KEEP_ALL：保留全部 | 激光雷达（仅需最新帧）；日志记录（全保存） | KEEP_ALL 可能导致内存溢出 |
| Liveliness（活性检测策略） | 检测节点活性：AUTOMATIC：系统自动检测；MANUAL_BY_TOPIC：手动上报活性 | 多机协作中的节点存活监控 | 活性检测增加约 5% 网络开销 |

ROS2 的系统结构：通信、工具、功能、社区。

### ROS 2 系统架构

ROS 2 的系统架构是由通信、工具、功能、社区四大部分组成的。

ROS = plumbing + tools + capabilities + community

**通信（Plumbing）**

ROS2 以 DDS（数据分发服务）替代传统通信实现，自动处理数据传输/解析/同步问题；通过标准化接口隔离模块功能，提供故障隔离能力，并内置通用接口，显著提升系统可维护性、扩展性与复用效率。

ROS2 四大核心通信方式：

- 话题（Topic）：在节点之间发送和接收消息
- 服务（Service）：客户端/服务器交互节点之间
- 动作（Action）：长时间任务
- 参数（Parameter）：使节点更具动态性

ROS2 四大核心通信方式：话题 Topic（一直在发布数据）。

一个节点既可以是发送方也可以是订阅方。

```Bash
ros2 topic list          # 查看当前所有话题
ros2 topic echo /chatter  # 监听某个话题数据
```

### 话题通信

**1. 话题通信（Topic）：单向、异步、流式数据传输**

特点：

- 单向通信：数据从发布方（Publisher）发送到订阅方（Subscriber）。
- 异步传输：订阅方不会主动向发布方请求数据，而是被动接收。
- 适用于流式数据：如传感器数据（激光雷达、摄像头、温度传感器），持续不断地产生数据。

例子：

- 机器人摄像头**每秒发布图像数据**，计算机视觉模块**订阅图像数据**并进行识别。
- 激光雷达**持续发布距离数据**，导航模块**订阅数据**并进行路径规划。

ROS2 四大核心通信方式：服务 Service（一个请求一个响应）。

```Bash
ros2 service list # 列出所有服务
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 2, b: 3}" # 发送服务请求加法运算
```

### 服务通信

**2. 服务通信（Service）：请求-响应机制**

特点：

- 双向通信：客户端（Client）请求，服务端（Server）响应。
- 同步交互：客户端等待服务端返回数据，任务完成后才继续执行。
- 适用于短时间任务：如查询传感器状态、执行一次性任务（打开开关）。

例子：

- 机器人请求路径规划服务：客户端发送起点和终点，服务器计算路径并返回路线。
- 查询温度传感器状态：客户端请求当前温度，服务端返回数值。

### 动作通信

**3. 动作通信（Action）：请求-反馈-最终结果**（一个请求一个响应,但是服务端会一直反馈进度）

```Bash
# 列出所有Action
ros2 action list
# 发送Action请求（让机器人移动）
# 让机器人导航到 map 坐标系下的 (x:1.0, y:2.0) 位置，朝向为正前方 (w:1.0)
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "{pose: {header: {frame_id: 'map'}, pose: {position: {x: 1.0, y: 2.0, z: 0.0}, orientation: {z: 0.0, w: 1.0}}}}"
```

特点：

- 客户端请求任务，服务端执行任务，并持续反馈进度。
- 适用于长时间任务：如机器人移动、机械臂抓取、导航等。
- 与服务通信类似，但能在执行过程中提供进度更新。

例子：

- 机器人导航到目标点：客户端请求移动到（x, y）位置，导航系统不断反馈当前位置，最终返回是否成功。
- 机械臂抓取任务：客户端请求抓取目标物体，机械臂反馈移动进度，最终返回抓取结果。

### 参数

**4. 参数服务（Parameter）：共享数据存储**

```Bash
# 列出当前所有参数
ros2 param list
# 获取某个参数信息
ros2 param get /robot max_speed
# 设置新的参数值
ros2 param set /robot max_speed 1.5
```

特点：

- 用于存储和管理机器人运行参数，如最大速度、传感器阈值。
- 服务端存储参数，客户端可以修改或读取参数。
- 适用于需要灵活调整的配置项。

例子：

- 调整机器人最大速度：无需修改代码，直接修改参数。
- 修改传感器灵敏度：通过参数服务实时调整阈值。

### 功能库与算法

ROS 生态系统是机器人软件的聚宝盆。无论开发者需要用于 GPS 的设备驱动程序、用于四足仿生机器人的步行和平衡控制器，还是用于移动机器人的地图系统，ROS 都能满足你的需求。从驱动程序到算法，再到用户界面，ROS 都提供了相关实现，开发者只需专注于自身应用程序即可。ROS 的目标是提供一站式的技术支持，降低构建机器人应用程序的门槛。ROS 希望任何开发者都可以将自己的创意变为现实，而无需了解底层软件和硬件的所有内容。

- 驱动程序（Drivers）：支持多种硬件，如激光雷达、摄像头、机械臂。
- 导航（Navigation）：提供 SLAM（同步定位与建图）、路径规划、障碍物检测等功能。
- 运动控制（Motion Control）：可用于四足机器人、机械臂等。
- 机器学习（Machine Learning）：可以集成 AI 进行目标识别、路径优化等任务。

## 理解与勘误

### 什么是具身智能

具身智能是一种**基于物理身体**进行感知和行动的**智能系统**，通过智能体**与环境交互获取信息**、**理解问题**、**基于环境做出决策并采取行动**以**实现某些目标**。

具身系统通过身体在环境中感知、决策、行动并接收反馈。大模型可承担语义和任务决策，但把模型装在机器人上不自动产生可靠运动能力。机械、执行器、传感器、动力学、控制与软件都影响实际行为。

课程介绍人形、四足、轮式等平台，以及机械设计、驱动、电气、计算、运动学、控制、感知与任务算法。应先确定任务和身体能力，再组织软件，不能把大模型当作所有关节控制的替代。

### ROS （机器人操作系统）究竟是什么

[ROS官方社区](https://www.ros.org/blog/community/)

ROS 是软件库、通信机制、工具、功能包和社区构成的机器人开发生态。Linux 提供进程、设备和网络，ROS 组织机器人模块。它不是保证硬实时的内核，也不会自动替你实现避障或稳定行走。

ROS 1 的 Master 主要负责名称注册与发现，节点数据通常直接传输，不能将所有消息理解为经 Master 转发。ROS 2 常用 DDS 与 RMW 中间件实现发现和通信；没有 ROS 1 式必需中心 Master。新版本也存在其他 RMW，实现不能永远等同于 DDS。

ROS 2 为嵌入式、多个机器人、QoS 和实时设计提供更合适的机制，但实际延迟仍取决于操作系统、执行器、内存、网络和节点代码。

### 包、可执行程序与节点

功能包组织代码、接口、配置和依赖；可执行程序是启动入口；节点是 ROS 图中的功能实体。一个进程可以包含多个节点，也可以让一个节点单独占一个进程。因此课件将节点等同于独立程序是入门简化，不是严格的一一关系。

例如相机节点发布图像，检测节点输出目标，定位节点估计位姿，规划节点给路径，控制节点输出速度。节点可以用 C++ 或 Python 写，也可以运行在不同机器。跨机还需环境、网络、类型和发现设置一致。

### 话题与消息

话题是有名字和类型的发布订阅通道。一个话题可有多个发布者和订阅者；同一节点也可同时发布和订阅不同话题。发布者不必知道订阅者身份，订阅者接收消息时调用回调。

话题适合传感器、状态和指令流，也可以只偶尔发布一次事件。课件中的一直发布不是必要定义。订阅了名字但消息类型不一致不能按正确语义通信，QoS 不兼容也可能看得到话题却收不到数据。

`.msg` 定义字段结构。例如 `Twist` 包含线速度和角速度，图像包含编码、尺寸和字节数据。话题名相同不证明坐标系、单位或控制语义相同，这些还需接口约定。

### 服务

服务是请求与响应接口，`.srv` 分开定义二者，适合查询状态和短操作。客户端可使用异步 Future，不必阻塞整个程序，因此课件关于客户端不能并行操作的说法不成立。

等待服务、发送请求、执行回调、检查返回与超时是不同阶段。服务通常不自带长任务反馈和取消协议。把耗时运动放进普通阻塞服务可能卡住回调；可改为动作或服务接受任务后另行查询状态。

### 动作

Action 组织目标、接受/拒绝、反馈、结果与取消，适合导航和长时间运动。`.action` 分别定义 Goal、Result 和 Feedback。动作底层使用若干服务与话题，不是额外的一种物理网络。

发送目标后要检查是否接受；接收中途反馈；结束时判断成功、取消还是中止。取消是请求，服务端可根据状态接受或拒绝，不能保证调用取消就立即安全停止全部电机。运动停止还依赖控制器和硬件链路。

### 参数

参数用于节点配置，常见类型有整数、浮点、布尔、字符串与数组。ROS 2 参数归属于节点，可通过参数服务读取和修改，并可发布参数事件。它不是 ROS 1 那种全局共享参数服务器。多个节点同名参数不自动共享值。

修改参数后是否立即生效取决于节点声明、验证和回调。改变坐标、关节映射或控制增益不能只看参数设置返回成功，还要验证模块是否重新配置。

### QoS 与跨机发现

Reliability 选择可靠或尽力传输；History/Depth 管理样本缓存；Durability 决定晚加入订阅者能否获得历史样本；Deadline、Lifespan、Liveliness 用于时效和活性约束。可靠传输不等于控制消息永远新鲜，队列过深可能传递旧数据。

传感器常采用 best effort，可靠订阅者通常不能匹配 best effort 发布者；best effort 订阅者可接受可靠发布者。应检查实际发布配置，而不是无条件把两端都改成 reliable。已通过 [ROS 2 官方 Humble 文档源码](https://github.com/ros2/ros2_documentation/blob/humble/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst) 核对可靠性兼容表。

跨机需核对 `ROS_DOMAIN_ID`、发现方式、防火墙、多播、网卡和 RMW。ROS 2 常用自动发现，不代表任何 Wi-Fi 或不同子网都无需配置。课件 X2 热点仅支持特定调试用途，是该产品网络限制，不能泛化成 ROS 2 不能无线组网。

### 常用工具如何帮助理解系统

RViz 订阅数据并可视化，不提供仿真物理；Gazebo 模拟物理、机器人和传感器；Launch 组织节点、参数与启动配置；rosbag2 记录和回放消息，帮助复现问题。回放时间需结合 `/clock` 与 `use_sim_time`，录下消息不保证录齐所有 TF 和配置。

TF 表达坐标系关系。标准移动系统常见 `map → odom → base_link → sensor`，map 校正可能跳变，odom 追求局部连续。每个 child frame 应由明确的一条父子关系负责，不能重复发布冲突变换。TF 不是把任意两个位置数值直接相加。

### 命令与复习

```bash
ros2 node list
ros2 node info /node_name
ros2 topic list -t
ros2 topic info /topic_name --verbose
```

### ROS 定义与比较表的补充说明

ROS 是机器人软件框架和生态，通常运行在 Linux 等操作系统之上。ROS 2 支持实时系统设计，但仅安装 ROS 2 或采用 DDS 不等于获得硬实时保证。

比较表中 ROS 1 的“仅支持 Linux”过于绝对，历史上也有 ROS 1 的 Windows 移植，参见 [微软 ROS on Windows](https://ms-iot.github.io/ROSOnWindows/index.html)。具体支持应按发行版和组件理解。ROS 1 的 TCPROS/UDPROS 是节点数据传输协议，ROS Master 负责注册与发现，并非所有消息都经 Master 转发。ROS 2 常用 DDS/RTPS，具体通信和发现行为还取决于 RMW 实现。

ROS 1 缺少内建的硬实时保证，不等于所有场景下都无法实现毫秒级普通响应，也不能把实时性问题仅归因于 TCP/IP。ROS 2 去除对 ROS Master 的依赖，不代表整个机器人系统完全没有单点故障。

QoS 表中的 Deadline 应解释为期望的相邻消息最大间隔，用于检测发布或接收是否按约定频率发生，不是每条消息的最大传输延迟。RELIABLE 提供重传等可靠性机制，也不承诺消息在任意故障和时限下必达。KEEP_ALL 仍受资源限制。10–30% 延迟和约 5% 网络开销缺少适用条件，不能作为通用性能结论。参考 [ROS 2 QoS 官方文档](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)。

服务采用请求与响应，但客户端可以异步调用；客户端是否阻塞取决于调用方式。“节点是独立运行的程序”是入门简化说法，一个进程可以包含多个节点。参数通常归属于各节点。参考 [ROS 2 节点](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Concepts/Basic/About-Nodes.rst)、[同步与异步服务调用](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/How-To-Guides/Sync-Vs-Async.rst)。
